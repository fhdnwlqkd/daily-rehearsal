# 면접 타입 Gemini API 실험 결과 3

## 1. 실험 목적

이번 실험은 지나치게 완벽한 모범 답변 대신 실제 전시 사용자가 말할 법한 중간 품질의 답변을 중심으로 진행했다.

- 브리핑의 정보량을 충분함부터 거의 무정보까지 낮춘다.
- 문항 답변의 품질을 평범하게 괜찮음, 짧음, 두루뭉술함, 질문 일부만 충족함, 회피로 나눈다.
- 각 답변의 평가뿐 아니라 다음 `sceneCue`, `opponentLine`, `actionPrompt`가 앞선 대화를 자연스럽게 이어받는지 확인한다.
- 두 번 실패한 뒤 `RECOVERY` 질문이 실제로 더 쉬워지는지 확인한다.

## 3. 브리핑 품질 범위

### B1. 충분하지만 평범한 브리핑

입력:

> 내일 백엔드 신입 면접이 있어요. 자기소개랑 팀 프로젝트 경험을 물어볼 때 말이 꼬일까 봐 걱정돼요. 너무 과하지 않게 차분하고 준비된 사람처럼 보이고 싶고 정장을 입을 생각이에요.

추출 결과:

```text
desired_persona = sharp_prepared
critical_moment = 자기소개 및 팀 프로젝트 경험 질문
outfit_direction = formal_clean
status = COMPLETED
```

필수 정보는 제대로 추출했다. 다만 `차분하고 준비된 사람`은 `calm_confident`와 `sharp_prepared` 사이의 경계인데 `sharp_prepared`로 선택했다. 틀렸다고 보기는 어렵지만 사용자 의도와 가장 가까운 option을 팀에서 확정할 필요가 있다.

### B2. 원하는 인상 누락

입력:

> 내일 개발자 면접이 있는데 자기소개하고 팀에서 갈등을 해결한 경험을 말하는 게 걱정돼요. 정장을 입고 갈 거예요.

초기 결과:

```text
desired_persona = null
critical_moment = 자기소개 및 팀 갈등 해결 경험 발표
outfit_direction = formal_clean
missingSlotKeys = [desired_persona]
followUpQuestions = [내일 어떤 인상을 남기고 싶나요?]
```

후속 답변:

> 엄청 자신만만하기보다는 차분하고 믿을 만한 사람으로 보이면 좋겠어요.

최종 결과는 `desired_persona=calm_confident`였다. 누락 탐지, 고정 질문, 후속 병합이 모두 자연스럽다.

### B3. 걱정 순간이 없는 브리핑

입력:

> 내일 면접이 있어요. 차분하고 준비된 인상을 주고 싶고 단정한 정장을 입고 싶어요.

실제 결과:

```text
desired_persona = sharp_prepared
critical_moment = 내일 면접
outfit_direction = formal_clean
status = COMPLETED
```

`critical_moment`에 연습할 순간이 아니라 상황 전체인 `내일 면접`이 들어갔다. 값이 비어 있지 않다는 이유로 완료되어 `가장 걱정되는 순간은 언제인가요?`가 나오지 않았다.

이 결과는 부적절하다. `critical_moment`는 단순 문자열 존재 여부뿐 아니라 질문, 자기소개, 갈등 경험처럼 시뮬레이션 장면으로 사용할 수 있는 구체성이 있는지 검증해야 한다.

### B4. 거의 정보가 없는 브리핑

입력:

> 내일 면접이 있어요.

초기 결과:

```text
desired_persona = null
critical_moment = 내일 면접
outfit_direction = null
missingSlotKeys = [desired_persona]
followUpQuestions = [내일 어떤 인상을 남기고 싶나요?]
```

후속 답변:

> 잘 모르겠어요. 그냥 면접을 무난하게 보고 싶어요.

최종 결과:

```text
desired_persona = calm_confident
critical_moment = 내일 면접
outfit_direction = neat_casual
status = COMPLETED
```

세션은 멈추지 않고 완료되지만, 실제 연습 목표가 없는 일반 면접 세션이 만들어진다. 이후 질문은 자기소개 답변에만 의존해 일반적인 기술 경험 질문으로 수렴했다.

### B5. 면접과 무관한 내용이 섞인 브리핑

입력:

> 내일 면접인데 오늘 비가 와서 늦게 일어났고 점심은 김치찌개를 먹었어요.

초기 결과:

```text
desired_persona = null
critical_moment = null
outfit_direction = null
missingSlotKeys = [desired_persona, critical_moment]
followUpQuestions = [
  내일 어떤 인상을 남기고 싶나요?,
  가장 걱정되는 순간은 언제인가요?
]
```

후속 답변:

> 긴장하지 않고 말하고 싶어요.

최종 결과:

```text
desired_persona = calm_confident
critical_moment = 긴장하지 않고 말하는 순간
outfit_direction = neat_casual
status = COMPLETED
```

무관한 원문을 slot으로 채우지 않은 점은 좋다. 그러나 두 질문에 한 문장으로 답했을 때 Gemini가 같은 문장을 persona와 critical moment 양쪽에 해석하여 완료했다. 허용 가능한 해석이지만 `critical_moment`의 장면 구체성은 낮다.

## 4. 평범한 답변의 합격선

### 통과한 답변의 최소 형태

다음 정도의 답변은 모두 `ACCEPTED`였다.

> 안녕하세요. 개발 직무에 지원했습니다. 프로젝트에서 백엔드 기능을 맡아본 경험이 있고, 모르는 부분은 찾아보면서 해결하는 편입니다.

> 안녕하세요. 개발 직무에 지원했습니다. 프로젝트에서 API를 만들었고 팀원들과 소통하면서 마무리한 경험이 있습니다.

완벽한 성과 수치나 화려한 표현이 없어도 다음 요소 중 두세 가지가 있으면 통과했다.

- 지원 직무
- 맡은 경험 또는 역할
- 문제 해결, 협업 같은 강점
- 실제로 취한 행동

Gemini는 부족한 성과나 구체성을 피드백으로 알려주면서도 흐름을 막지 않았다. 이번 실험에서 가장 의도에 맞는 판정이다.

### 재시도가 필요했던 답변

다음 답변은 `RETRY_REQUIRED`였다.

```text
안녕하세요. 저는 그냥 성실한 편이고 시키는 일은 열심히 합니다.
안녕하세요. 개발 직무 지원자입니다. 프로젝트를 했고 학교도 열심히 다녔습니다.
에러가 나서 검색해보고 코드를 고쳤습니다.
의견이 다르면 서로 이야기해서 정했습니다.
그냥 익숙한 기술이라서 선택했습니다.
```

공통점은 직무·상황을 언급하더라도 본인의 역할, 행동, 판단 근거가 없다는 것이다. 재시도 피드백도 빠진 요소를 정확히 짚었다.

## 5. 정상 3턴 흐름

### R1. 충분한 브리핑과 평범하게 괜찮은 답변

#### 턴 1

- 답변: 학교 프로젝트에서 API 개발을 맡았고 팀원과 문제 원인을 찾아 해결했으며 맡은 일을 끝까지 한다고 설명
- 결과: `ACCEPTED`
- 피드백: `배울 점이 많다`보다 기술 역량을 자신 있게 강조하라고 안내

#### 턴 2

질문:

> 팀 프로젝트에서 기술적인 문제를 해결했던 구체적인 사례 하나만 더 자세히 설명해주실 수 있을까요?

답변:

> API 응답에 화면에서 필요한 값이 빠져서 연동이 안 된 적이 있습니다. 프론트 팀원과 필요한 필드를 다시 정리하고 응답 구조를 수정한 뒤 테스트를 추가해서 해결했습니다.

결과: `ACCEPTED`

#### 턴 3

질문:

> 그 과정에서 어떤 기술 스택을 사용하셨나요? 그리고 그 문제를 해결할 때 본인만의 기술적인 고민이나 기준이 있었는지 궁금합니다.

행동 요구:

> 사용했던 기술 스택을 언급하고, 문제를 해결할 때 고려했던 기술적 기준이나 원칙을 구체적으로 설명해보세요.

답변은 Spring Boot, 응답 일관성, 기존 화면 호환성, 테스트 확인 정도로 말했다. 결과는 `ACCEPTED`였다.

질문이 `경험 -> 구체적인 문제 -> 기술 선택 기준`으로 자연스럽게 깊어졌다.

### R2. 부실한 브리핑과 평범한 답변

브리핑의 `critical_moment`는 `내일 면접`에 불과했다. 따라서 첫 답변에서 나온 `프로젝트`, `백엔드`, `문제 해결`을 중심으로 질문이 생성됐다.

턴 2 첫 답변 `에러가 나서 검색해보고 코드를 고쳤습니다`는 재시도였고, 다음처럼 보강하자 통과했다.

> 로그를 확인해 보니 빈 값 처리에서 오류가 났습니다. 입력값 검사를 추가하고 같은 문제가 다시 생기지 않게 테스트도 작성했습니다.

턴 3은 사용한 기술과 선택 이유를 물었다.

1. `그냥 익숙한 기술이라서 선택했습니다.` -> `RETRY_REQUIRED`
2. Spring 요청 검증이 반복 검사를 줄이고 요청 단계에서 오류를 막는다고 설명 -> `ACCEPTED`

브리핑이 부실해도 앞선 사용자 답변을 기반으로 대화는 성립했다. 다만 사용자 맞춤형 면접이라기보다 보편적인 백엔드 면접으로 바뀐다.

### R3. 무관한 브리핑과 부실한 첫 답변

첫 답변 `성실하고 시키는 일을 열심히 한다`는 재시도였다. 프로젝트 기능 구현과 문제 해결을 추가하자 통과했다.

이후 흐름:

```text
기술적 난관 질문
-> 빈 요청값으로 발생한 서버 오류와 검증 추가 답변
-> 팀원과 의견 충돌을 어떻게 조율했는지 질문
```

브리핑은 거의 쓸 수 없었지만 통과된 답변 이력을 이용해 기술 문제에서 협업으로 자연스럽게 전환했다.

### R4. 갈등 경험 브리핑과 일부만 답한 자기소개

브리핑의 `critical_moment`가 `팀 갈등 해결 경험`이었기 때문에 턴 2부터 갈등 질문으로 이어졌다.

```text
팀원들과 의견 차이가 있었던 사례
-> 빠른 구현과 테스트 우선순위를 절충한 답변
-> 상대를 설득할 때 사용한 구체적인 대화 방식 질문
```

마지막 답변에서 상대의 일정 압박을 먼저 듣고 핵심 기능과 필수 테스트를 함께 제안했다고 설명하자 `ACCEPTED`였다. 네 정상 흐름 중 브리핑의 맞춤성이 가장 잘 반영된 사례다.

## 6. 연속 실패와 RECOVERY

R5는 브리핑에서 `critical_moment=내일 면접`만 추출된 세션이다.

### 턴 1

1. `안녕하세요. 열심히 하겠습니다.` -> `RETRY_REQUIRED`
2. `딱히 할 말이 없는데 다음 질문으로 넘어가면 안 될까요?` -> `FORCED_ADVANCE`

### 턴 2

`generationMode=RECOVERY`였지만 생성 내용은 다음과 같았다.

```text
sceneCue = 자기소개를 마친 후, 면접관이 지원자의 구체적인 성과에 대해 질문합니다.
opponentLine = 이전 프로젝트에서 가장 큰 성과를 냈던 경험 하나만 구체적으로 말씀해주시겠어요?
actionPrompt = 본인의 역할과 구체적인 성과를 수치나 결과 중심으로 설명하세요.
```

문제점:

- 자기소개는 성공하지 않았는데 `자기소개를 마친 후`라고 가정했다.
- `RECOVERY`인데 질문 난이도가 낮아지지 않았다.
- 구체적인 수치와 가장 큰 성과를 요구하여 오히려 부담이 커졌다.

다음 정도의 답변도 첫 시도에서 실패했다.

> 학교 프로젝트에서 API 하나를 맡았습니다. 처음에는 잘 몰랐지만 문서를 찾아보고 팀원에게 물어보면서 끝까지 완성했습니다.

두 번째 답변에서 오류 조건, 로그, 검증, 테스트까지 설명했지만 결과는 `FORCED_ADVANCE`였다. 코드상 두 번째 답변도 Gemini가 `accepted=true`를 반환하면 `ACCEPTED`가 된다. 따라서 이 답변은 Gemini가 다시 거절한 경우다. 다만 서버가 Gemini의 원래 피드백을 `두 번의 연습을 마쳤어요`로 덮어써 정확한 거절 이유를 확인할 수 없다.

### 턴 3

다시 `generationMode=RECOVERY`였고 턴 2의 질문과 `sceneCue`, `opponentLine`, `actionPrompt`가 사실상 그대로 반복됐다.

사용자가 협업 갈등 답변을 하자 질문 불일치로 재시도를 받았고, 구체적인 갈등 사례로 보강해도 두 번째 시도라 `FORCED_ADVANCE`가 됐다.

### RECOVERY 결론

현재 recovery 흐름은 의도와 다르게 동작한다.

1. 실패한 발화를 대화 이력에서 제외하는 것은 맞다.
2. 그러나 이전에 성공한 내용이 없으므로 생성기가 같은 recovery fallback 질문을 반복한다.
3. `범위를 좁힌 질문으로 한 가지 경험부터 설명하게 한다`는 설정이 실제로는 `가장 큰 성과와 수치`를 요구하는 어려운 질문으로 변형됐다.
4. 생성 문구가 실패한 자기소개를 성공한 것처럼 가정한다.

## 7. 이상 여부 판정

### 자연스러웠던 부분

- 평범하지만 핵심이 있는 자기소개를 통과시키고 개선점만 안내했다.
- 첫 답변에서 언급한 API, 오류 해결, 협업을 후속 질문의 소재로 사용했다.
- 짧고 추상적인 답변에는 구체적으로 무엇이 빠졌는지 알려줬다.
- 갈등 브리핑이 있으면 기술 질문 일변도에서 벗어나 협업과 설득 질문으로 이어졌다.
- `sceneCue`, `opponentLine`, `actionPrompt`의 역할 구분은 정상 흐름에서 잘 지켜졌다.

### 수정이 필요한 부분

1. `critical_moment="내일 면접"`을 유효한 순간으로 인정한다.
2. 부실한 브리핑이 완료되면 질문이 보편적인 기술 난관과 기술 스택으로 수렴한다.
3. 기술 답변마다 기술 스택과 선택 근거를 묻는 패턴이 반복된다.
4. `RECOVERY` 질문이 더 쉬워지지 않고 성과 수치까지 요구한다.
5. 실패한 자기소개를 `잘 들었다`, `마쳤다`고 가정한다.
6. 연속 recovery에서 같은 질문과 행동 요구를 반복한다.
7. 두 번째 실패 시 Gemini의 구체적인 피드백을 서버 고정 문구가 덮어써 마지막 개선점을 알 수 없다.

## 8. 튜닝 제안

### 우선순위 1. Critical moment 유효성

다음 값은 비어 있지 않더라도 누락으로 취급하는 규칙이 필요하다.

```text
면접
내일 면접
면접 보는 순간
잘 모르겠음
그냥 무난하게
```

구체적인 질문 종류나 행동 장면으로 사용할 수 있는 값만 확정해야 한다.

### 우선순위 2. RECOVERY 계약 강화

prompt에 다음 규칙을 명시하는 편이 좋다.

- 직전 질문보다 반드시 짧고 쉬운 질문을 만든다.
- 수치, 최대 성과, 복수 조건을 요구하지 않는다.
- 하나의 역할 또는 행동만 묻는다.
- 실패한 답변을 들었다거나 성공적으로 마쳤다고 말하지 않는다.
- 직전 `opponentLine`과 동일하거나 의미상 같은 질문을 반복하지 않는다.

면접 recovery 예시:

```text
어떤 프로젝트를 했는지 하나만 골라주세요.
그 프로젝트에서 맡은 역할은 무엇이었나요?
문제가 생겼을 때 가장 먼저 한 행동은 무엇이었나요?
```

### 우선순위 3. 질문 다양성

보편 면접에서도 세 턴이 모두 기술 깊이로만 흐르지 않도록 질문 축을 분산할 수 있다.

- 역할과 강점
- 문제 해결
- 협업과 갈등
- 배우는 방식
- 지원 동기
- 모르는 질문에 대응하는 태도

단, 브리핑에 특정 걱정 순간이 있으면 해당 축을 우선한다.

### 우선순위 4. 마지막 피드백 보존

현재 판정 정책은 다음과 같다.

```text
accepted=true                         -> ACCEPTED
accepted=false, 아직 시도 가능       -> RETRY_REQUIRED
accepted=false, 마지막 시도          -> FORCED_ADVANCE
```

판정 자체는 의도와 일치한다. 문제는 마지막 시도의 Gemini 피드백을 서버의 `두 번의 연습을 마쳤어요. 다음 단계로 넘어갈게요.`가 완전히 대체한다는 점이다. `다음 단계로 진행한다`는 안내와 Gemini가 남긴 마지막 개선점을 함께 반환하거나 별도 필드로 분리하는 편이 좋다.

## 9. 최종 결론

정상 범위에서는 현재 Gemini 흐름이 상당히 자연스럽다. 지나치게 완벽하지 않은 답변도 핵심 역할과 행동이 있으면 통과하며, 앞선 답변을 활용한 꼬리질문과 행동 요구도 대체로 적절하다.

가장 큰 문제는 브리핑의 `critical_moment` 품질 검증과 연속 실패 뒤 `RECOVERY`다. 특히 recovery는 현재 사용자를 돕는 완충 장치가 아니라 더 어려운 질문을 반복하는 경로가 될 수 있다. 면접 튜닝은 정상 질문 문구를 더 다듬기 전에 이 두 경계를 먼저 고치는 것이 좋다.
